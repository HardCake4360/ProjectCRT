# ProjectCRT 데모 요구사항 분석 및 순차 수행 계획

검토일: 2026-10-19 (Asia/Seoul)

## 1. 결론과 검토 범위

현재 프로젝트는 **대화·조사 기능과 재사용 가능한 진행 시스템을 갖춘 프로토타입**이다. 계획서가 요구하는 **하나의 살인사건을 처음부터 보고·평가까지 해결하는 데모**의 완성은 확인할 수 없다. 가장 큰 공백은 UI 수보다 사건 정답 데이터, NPC별 지식·진술 규칙, 사건 진행 상태, 종결·평가의 연결이다.

분석 기준은 사용자 제공 `C:/Users/user/Downloads/데모_완성_계획서.txt`이다. 문서의 권장 순서와 작업 지시는 요구사항으로 분석했으며 구현 승인으로 간주하지 않았다. 게임 코드·씬·설정을 변경하지 않았다.

현재 작업 폴더의 수정 파일과 미추적 파일까지 포함해 검토했다. Git HEAD만의 분석이 아니다. 코드, Unity 직렬화 데이터, 문서, 외부 서버의 관련 소스를 읽었다. 이번 검토에서 Unity 플레이, 새 컴파일·테스트 실행, 서버 요청, 독립 실행 빌드는 수행하지 않았다. 따라서 아래 ‘부분 충족’은 구현 근거가 있다는 뜻이며 실제 플레이 합격을 의미하지 않는다.

## 2. 요구사항의 구조

### 필수 플레이 경험

시작 → 현장 및 레베카와 시신 발견 → 여러 NPC 대화 → 정보 기록·진위 판단 → 다른 NPC에게 근거 제시 → 모순 확인·진술 전환 → 사건 결론 → LSPD 복귀 → 보고·평가.

핵심은 자유 대화 자체가 아니라 **대화에서 얻은 정보가 다음 조사 행동과 사건 해결을 실제로 바꾸는 순환**이다.

### 확정 조건

- 로스 시뮬라의 바에서 발생한 살인사건이며 범인은 손님 중 한 명이다.
- 주인공이 현장에서 바 주인 레베카와 함께 시신을 발견한다.
- 레베카를 포함해 최소 5명의 인물이 등장하고 성격·말투가 구별된다.
- 획득 정보에 진실/거짓/보류를 선택하고 나중에 수정한다.
- 플레이어 판단, 실제 사실, NPC의 인식, 실제 발언을 구별한다.
- 단계·조건에 따라 행동과 진술이 변하며 네 가지 진술 유형을 설계한다.
- NPC ID, 정보 ID, 단계 ID로 문서와 런타임 데이터를 연결한다.

### 아직 확정하면 안 되는 항목

바 이름, 피해자·범인·동기·수법, 시신 위치, 추가 인물, 전환 조건, 평가 기준, 플레이 시간과 일정은 원문에서도 미정이다. 기존 샘플의 설정을 정식 정답으로 승격하지 않는다. 최소 5명에 피해자를 포함하는지도 인물표에서 명시해야 한다. 설계 제안은 **대화 가능한 인물 5명과 피해자를 별도로 두는 것**이다.

## 5. 구현에서 확인한 주요 공백

1. **정보 DB는 아직 사건 DB가 아니다.** `InvestigationItemDefinition`은 ID·분류·설명·프롬프트·태도 임계값·다음 항목만 가진다. 실제 진위, 출처 NPC, 모순 관계, NPC별 믿음, 단계 조건 모델이 없다. `InvestigationInventorySaveData` v1은 해금 ID 목록만 저장한다.
2. **실제 데이터가 샘플 수준이다.** `Assets/resources/Investigation/InvestigationItemDatabase.asset`에는 old_tv 한 항목만 등록되어 있다. old_tv는 test 항목을 followingItem으로 참조하지만 test는 DB 목록에 없다. 해금 ID가 저장되어도 정의 조회·표시가 누락될 수 있으므로 우선 정비 대상이다. 빈 ID의 InvestigationItem 자산도 존재한다.
3. **대화 기록과 사건 정보 획득은 다르다.** `NpcInvestigationController`는 답변을 대화 상태에 저장하고, 첨부 정보의 임계값 만족 시 followingItem을 해금한다. 임의의 NPC 발언이 자동으로 정식 정보 ID가 되는 구조로 볼 수 없다. 서버의 unlockTopicIds는 현재 명시적으로 무시한다.
4. **TII/tell은 실제 진위 기준이 아니다.** 클라이언트는 답변과 tell API를 분리 호출한다. 외부 서버의 `_derive_tell_llm(question_text, persona)`는 질문·페르소나 기반 분류 경로다. 원문이 설명한 ‘발언 진실 여부 확인’과 동일한 의미로 단정할 수 없다. 지표의 의미와 게임상 정확도를 명세하고, 사건의 실제 진위 및 플레이어 판단과 분리해야 한다.
5. **단계의 단일 관리자가 없다.** `InvestigationContextBuilder.phase`는 기본 문자열 investigation이다. 기존 StoryState와 RPG GameState, 조사 JSON 저장을 어떤 기준으로 동기화할지 정해야 한다. 기존 퀘스트 골격과 RPG 조건 시스템을 동시에 별도 확장하면 진행 상태가 갈라질 수 있다.
6. **페르소나 수가 사건 인물 수는 아니다.** 외부 폴더에는 rebecca·jeremy 외 기존 캐릭터 JSON도 있지만, 이를 바 사건의 다섯 인물로 볼 근거는 없다. 서버 코드는 reply/tell 경로와 phase 전달을 지원하나 정식 사건 지식 제한을 보장하는지는 별도 검증이 필요하다.
7. **새 게임·재시작 정책이 필요하다.** 자동 로드하는 조사 인벤토리, NPC 대화 저장, 서버의 플레이어·페르소나별 로그/요약, RPG 슬롯이 함께 남으면 이전 플레이가 다음 데모에 영향을 줄 수 있다. 사건/세션 식별과 초기화 범위를 통합해야 한다.

## 6. 권장 구현 방향

**기존 Bar와 조사 UI를 플레이 기반으로 유지하고, RPG의 조건·이벤트·저장 기반을 필요한 범위부터 연결하는 방식**을 권장한다. 데모를 위해 모든 기존 씬을 격자 RPG 맵으로 바꾸는 작업은 선행 필수 조건이 아니다. 적용 가능성은 단계 0의 작은 연결 검증으로 확정한다.

- 사건 상태는 하나의 관리 경로로 모은다. 단계, 획득 정보, 플레이어 판단, NPC 진술 전환, 종결·보고를 공통 세션에서 읽는다.
- 기존 공용 인벤토리는 획득 정보의 표시·심문 선택 창구로 재사용한다. RPG 상태와 별도 정답을 갖지 않도록 어댑터 또는 저장 통합 정책을 만든다.
- 실제 사실은 설계 데이터가 결정하고 LLM은 현재 NPC에게 허용된 지식·진술을 표현한다. 자유 생성 답변만으로 사건 정답이나 단계 완료를 확정하지 않는다.
- 정보 정의와 플레이 기록을 구분한다. 정보 정의에는 정답·관계·획득 조건, 플레이 기록에는 출처 NPC/진술/획득 시점/판단/판단 변경을 둔다.
- NPC의 믿음과 발언을 분리한다. 잘못 알고 한 정직한 진술과 고의적인 거짓말의 차이를 평가 기준에 반영한다.
- 단계 완료·정답 판정은 결정적인 규칙으로 처리한다. 미발견 정보나 숨겨진 정답을 NPC 대화 요청에 무차별로 보내지 않는다.

각 단계의 완료 조건을 충족한 후 다음 단계로 이동한다. 시간 추정은 목표 플레이 시간과 제작 인원 확정 후 작성한다.

| 순서 | 수행 내용 | 산출물 | 완료 조건 |
| --- | --- | --- | --- |
| 0 | 현재 실행 기준선 및 통합 방식 확정 | 실행 절차, 시작 씬, 상태·저장 소유권 표, API 계약 | Bar에서 두 NPC 대화·정보 공유·씬 왕복 확인, reply/tell 실제 연결 확인. RPG 상태→기존 조사 컨텍스트의 작은 연결 검증 |

| 5 | 처음부터 끝까지 경험·평가 확정 | 전체 진행 시나리오, 보고 양식·채점표 | 도입/발견/조사/종결/복귀/보고·평가의 대사·안내·전환 정의. 오답·정보 부족 시 처리도 정의 |
| 6 | 데이터 모델과 저장·검증 기반 확장 | 사건/NPC/정보/단계 정의, 기록 DTO, 참조 검사기 | 빈·중복 ID, 끊긴 참조, 조건 누락 검출. 정답·믿음·발언·판단 분리. 기존 저장 이전·새 게임 초기화 정책 검증 |
| 7 | 정보 획득·판단 UI 완성 | 획득 즉시 판단 UI, DB 편집·출처 표시 | 진실/거짓/보류 선택 및 수정·저장·복원. 보류로 진행 가능. 재획득이 기존 판단을 덮어쓰지 않음 |
| 8 | 작은 조사 흐름의 통합 검증 | 두 NPC와 최소 증거·정보로 된 조사 루프 | 대화→기록→판단→다른 NPC 제시→조건부 진술 전환→단계 완료가 실제 실행됨 |
| 9 | 정식 사건·전체 인물·레벨 구현 | 바 현장, 발견 연출, 5명 이상 인물과 사건 데이터 | 모든 필수 정보·분기 연결, NPC별 차별화, 해결 전 성급한 종결 차단, 안내로 막힘 해소 |
| 10 | 해결·LSPD 복귀·보고·평가 구현 | 결론 제출, 이동, 보고서, 평가 결과 | 올바른/잘못된 결론에 정의된 결과 표시. 기존 단순 씬 이동과 사건 완료 조건 연결 |
| 11 | 데모 인수 검증 및 배포 빌드 | 원문 10개 기준별 결과·증거, 실행 가이드 | 새 게임부터 평가까지 수동 완주와 독립 실행 빌드 성공. 반복 실행·서버 장애·저장 복원 확인 |

단계 8을 중간 통과 기준으로 둔다. 여기서 핵심 순환을 증명하기 전에 전체 인물·연출을 늘리면 데이터와 시스템을 동시에 다시 수정할 위험이 크다. 최종 장면 완주 골격은 단계 5의 명세에 따라 단계 8 이후 확장한다.

## 8. 권장 문서·데이터 묶음

아래는 새로 작성할 문서 제안이며 현재 생성·확정된 사건 내용이 아니다.

1. 사건 시나리오: 정답, 시간표, 관계, 발견 상황.
2. 정보 DB: information/evidence/topic ID, 실제 진위, 출처, 획득 조건, 관련·모순 관계, 제시 대상.
3. NPC 페르소나: npc ID, 역할·성격·말투·관계·목표.
4. NPC 지식·진술표: 정보 ID, 믿음, 진실·거짓 발언, 진술 유형.
5. 단계 정의: phase ID, 진입/완료 조건, 공개 범위, 다음 단계.
6. NPC×단계 지침: 행동·공개/은폐 범위·진술 전환 조건.
7. 전체 진행 및 평가: 씬·안내·이벤트·보고·평가·막힘 회복 경로.

공통 ID와 스키마를 먼저 합의하고, 문서와 게임 데이터의 중복 수작업 입력을 줄인다. 평가 기준이 사건 데이터와 다른 정답을 참조하지 않도록 같은 정의를 사용한다.

## 9. 검증 계획과 우선순위

**가장 먼저:** 실행 기준선, 사건 정답·해결 경로, 상태 소유권, 진위/판단 모델, 정보 DB 참조 정비.

**그다음:** 두 NPC 통합 조사, 전 인물·단계 확장, 시작~복귀~보고·평가 연결.

**마지막:** 연출·안내·말투 품질 조정과 배포 검증. 미사용 전투·생존 등은 데모 완성의 필수 작업에 넣지 않는다.

검증에는 다음을 포함한다.

- 데이터: ID 유일성·참조 무결성·필수 정보 도달 가능성·의도된 모순과 오류 구분.
- 상태: 진술 전환 전후, 순서가 다른 조사, 중복 제시, 조건 미달, 슬롯 복원, 새 게임 초기화.
- 대화: 알 수 없는 정보 비공개, 사건 정답 유지, NPC 간 기억 분리, 재질문 시 일관성, 네 진술 유형.
- UI: 획득 즉시 판단, 보류·수정, 출처 확인, 증거 제시, 대화/DB/씬 전환의 입력·카메라 복구.
- 장애: reply/tell 중 하나만 실패, 지연·재시도, 중복 해금 방지, 안내 및 진행 복구. 오프라인 대사 대체는 별도 제품 결정이다.
- 인수: 정상 해결, 잘못된 결론, 판단 변경, 비선형 조사, 저장 후 재개를 검증하고 빌드에서 처음부터 끝까지 완주.

2026-10-09의 기존 보고는 EditMode 273개, PlayMode 96개 통과를 기록하지만 **RPG 이식 및 샘플 검증 결과**다. LLM 조사 통합·정식 살인사건·보고 평가의 합격 증거로 사용할 수 없다.
